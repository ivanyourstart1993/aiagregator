fal.ai is a real model aggregator, not a vendor we're debunking — if you're comparing it to Aigenway, you already know the pitch: one API surface in front of many independently-trained image, video and text models. The actual differences show up once you're in production: how you read your balance, whether every model shares one request shape, and whether webhooks are signed by default.

## Where fal.ai and Aigenway overlap

Both platforms exist for the same reason: nobody wants a separate account, key and billing dashboard per model provider. fal.ai runs its own hosted inference for a wide catalog of image, video and audio models behind a single API key, and so does Aigenway. If you're evaluating a fal.ai alternative because you want a second aggregator to compare pricing or reliability against, not because fal.ai is broken, that's a fair reason to look — list what's live on your account and compare directly:

```bash
curl "https://api.aigenway.com/v1/methods?provider=google_banana" \
  -H "Authorization: Bearer sk_live_..."
```

## Prepaid USD you read from the API, not credits you estimate

fal.ai bills in its own credit units, which means converting a per-call cost back to real currency before you can forecast spend. Aigenway keeps the balance in USD and exposes it as a plain `GET`, so a script can check funds before queuing a batch instead of guessing from a credits-remaining widget:

```bash
curl https://api.aigenway.com/v1/balance \
  -H "Authorization: Bearer sk_live_..."
```

Top up in dollars, spend in dollars, and the number your code reads back matches the number on the invoice — no conversion table to keep in sync as a provider's per-call cost changes.

## One task contract for every model

fal.ai's per-model endpoints each define their own input schema, so switching from one model to another means reading a new API reference and reshaping your payload. On Aigenway every model — image, video or text — takes the same envelope: `provider`, `model`, `method`, `params`. Only `params` changes shape between models; the request, the response, and the task states around it stay identical:

```bash
curl -X POST https://api.aigenway.com/v1/generations \
  -H "Authorization: Bearer sk_live_..." \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "google_banana",
    "model": "imagen-4.0-ultra-generate-001",
    "method": "text_to_image",
    "params": {
      "prompt": "a lighthouse at dusk, storm clouds gathering, dramatic side lighting",
      "aspect_ratio": "16:9"
    }
  }'
```

`Idempotency-Key` makes retries safe — resend the same key after a dropped connection and you get the same task back instead of paying for a duplicate render.

## Signed webhooks instead of a polling loop you build yourself

Every generation, on any model, returns a task in `queued` or `processing` state — nothing here is synchronous. Set a `callback_url` on the request and Aigenway `POST`s the finished task to your endpoint the moment it's ready, signed with an HMAC so you can verify the payload actually came from the gateway:

```bash
curl -X POST https://api.aigenway.com/v1/generations \
  -H "Authorization: Bearer sk_live_..." \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "kling",
    "model": "kling-v2-master",
    "method": "text_to_video",
    "params": { "prompt": "drone shot rising over a foggy pine forest", "duration": 5 },
    "callback_url": "https://your-app.example.com/webhooks/aigenway"
  }'
```

The callback arrives with an `X-Aggregator-Signature: sha256=<hex>` header — an HMAC over the raw body keyed with your webhook secret — plus `X-Aggregator-Event` and `X-Aggregator-Task-Id`, so your endpoint can reject anything that isn't genuinely from the gateway before it acts on the payload. Details, including the verification snippet, are in the [webhooks](/docs/webhooks) docs.

## Why this matters once you're past the demo

A single well-run aggregator gets a project a long way; the friction shows up at scale, when finance wants spend in dollars and a security review wants webhook signatures, not an honor system. What Aigenway adds on top of the same multi-model breadth:

- **A balance you can read, not estimate.** Prepaid USD in, USD out — one `GET /v1/balance` call, no credit-to-dollar conversion.
- **One contract, every model.** `provider` / `model` / `method` / `params` never changes shape, so a new model is a config change, not a new integration.
- **Signed webhooks by default.** Every callback carries an HMAC signature and task/event headers, so verifying a webhook is a few lines, not a trust assumption.

If fal.ai's catalog and pricing already fit, there's no reason to move a working integration. If you're standing up a new one and want a USD balance you can check programmatically, one request shape across every model, and webhooks you can verify instead of just trust, that's what switching buys you.
