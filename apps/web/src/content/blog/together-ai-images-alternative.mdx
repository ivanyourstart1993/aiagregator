Together AI is a real inference platform, not a vendor we're debunking — its images endpoint sits alongside its LLM catalog behind one API key, which is exactly the pitch Aigenway makes across image, video, and text. The differences that matter show up once you're in production: how you read your balance, whether every model shares one request shape, and whether webhooks are signed by default.

## Where Together AI and Aigenway overlap

Both platforms solve the same problem: nobody wants a separate account, key, and billing dashboard per model owner. Together AI puts FLUX-family and other image models behind the same key as its text models, and Aigenway does the same across image, video, and text providers from many vendors. If you're evaluating a Together AI images alternative because you want a second gateway to compare pricing or reliability against — not because Together AI is broken — that's a fair reason to look. List what's live on your account and compare directly instead of trusting a marketing page:

```bash
curl "https://api.aigenway.com/v1/methods?provider=kling" \
  -H "Authorization: Bearer sk_live_..."
```

## Prepaid USD you read from the API, not a running-total dashboard

Together AI bills usage against a payment method on file, with per-model rates you look up on a pricing page and a running total you check in the console. Aigenway keeps a prepaid USD balance and exposes it as a plain `GET`, so a script can check funds before queuing a batch instead of switching to a browser tab:

```bash
curl https://api.aigenway.com/v1/balance \
  -H "Authorization: Bearer sk_live_..."
```

Top up in dollars, spend in dollars, and the number your code reads back is the number that gets debited — no per-model rate card to reconcile against a monthly invoice before you can forecast spend.

## One task contract for every model

Together AI's image endpoint follows its own request shape, separate from its chat completions shape, so adding an image model still means reading that endpoint's parameters and reshaping your payload. On Aigenway every model — image, video, or text — takes the same envelope: `provider`, `model`, `method`, `params`. Only `params` changes shape between models; the request, the response, and the task states around it stay identical:

```bash
curl -X POST https://api.aigenway.com/v1/generations \
  -H "Authorization: Bearer sk_live_..." \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "kling",
    "model": "kling-v2-master",
    "method": "text_to_video",
    "params": {
      "prompt": "a lighthouse beam sweeping across a foggy harbor at night",
      "duration": 5
    }
  }'
```

`Idempotency-Key` makes retries safe — resend the same key after a dropped connection and you get the same task back instead of paying for a duplicate render.

## Signed webhooks instead of a polling loop you build yourself

Every generation, on any model, returns a task in `queued` or `processing` state — nothing here is synchronous. Set a `callback_url` on an Aigenway request and the gateway `POST`s the finished task to your endpoint the moment it's ready, signed with an HMAC so you can verify the payload actually came from the gateway:

```bash
curl -X POST https://api.aigenway.com/v1/generations \
  -H "Authorization: Bearer sk_live_..." \
  -H "Idempotency-Key: $(uuidgen)" \
  -H "Content-Type: application/json" \
  -d '{
    "provider": "google_banana",
    "model": "imagen-4.0-ultra-generate-001",
    "method": "text_to_image",
    "params": { "prompt": "overhead shot of a terraced rice field after rain" },
    "callback_url": "https://your-app.example.com/webhooks/aigenway"
  }'
```

The callback arrives with an `X-Aggregator-Signature: sha256=<hex>` header — an HMAC over the raw body keyed with your webhook secret — plus `X-Aggregator-Event` and `X-Aggregator-Task-Id`, so your endpoint can reject anything that isn't genuinely from the gateway before it acts on the payload. Details, including the verification snippet, are in the [webhooks](/docs/webhooks) docs.

## Why this matters once you're past the demo

A single well-run inference platform gets a project a long way; the friction shows up at scale, when finance wants spend in dollars up front and a security review wants webhook signatures, not an honor system. What Aigenway adds on top of comparable image-model breadth:

- **A balance you can read, not a dashboard you check.** Prepaid USD in, USD out — one `GET /v1/balance` call, no rate card to reconcile against a monthly invoice.
- **One contract, every model.** `provider` / `model` / `method` / `params` never changes shape, so adding a model is a config change, not a new integration against a new endpoint schema.
- **Signed webhooks by default.** Every callback carries an HMAC signature and task/event headers, so verifying a webhook is a few lines, not custom work per provider.

If Together AI's image endpoint already fits your stack, there's no reason to move a working integration. If you're standing up a new one and want a USD balance you can check programmatically, one request shape across every model, and webhooks you can verify instead of just trust, that's what switching buys you.
